## 完整备份恢复协议（实施前收敛）

- V2 文件含 `schemaVersion: 2`、`exportedAt` 及六类数组 `problems/drafts/submissions/progress/plans/settings`；现有 schemaVersion 1 文件的蛇形字段在恢复时规范化。认证、会话及备份中的 `user_id` 一律忽略。
- 新 `/api/backup/manifest` 返回各类数量，`/api/backup/:kind?offset=&limit=` 分页导出；浏览器拼装一个私有 JSON 文件。保留旧 `/api/export`，新 UI 改走分页接口，避免一次生成最大约 200 道题的巨大 JSON。
- 浏览器逐条调用 `POST /api/restore/preview`；同一条记录随后送入 `POST /api/restore`。每次请求仅一条，JSON body 上限 2500 KiB，规范化单条数据上限 1800 KiB；超过则写入前拒绝。这覆盖现有字段长度允许的绝大多数 UTF-8 内容，同时守住 D1 单行 2 MB 上限。顺序为题目、草稿、历史、进度、计划、设置；这样题目 ID 映射先可用。浏览器汇总预览与恢复的新增、合并、跳过、失败数量；部分批次不会报告为完成，失败可在原文件上重试。
- 文件 SHA-256 生成稳定 `batchId`。D1 `restore_entries` 以 `(user_id,batch_id,kind,source_key)` 唯一标识成功创建/映射的条目，保存输入摘要、目标题目 ID 和结果。每条业务写入与该记录同一 `db.batch` 事务；重复请求返回已存结果，批次内同键不同内容拒绝。配额、冲突和悬空记录不落成功账本，后续重试可重新评估。每用户恢复账本最多 10000 条。每次写入查询量远小于 D1 Free 每次调用 50 查询上限。
- 0002 迁移以触发器维护每用户数据修订号。导出时每页核对修订号并在末尾再读 manifest；任何跨标签写入导致版本变化就拒绝本次拼装，要求重新导出。
- 预览与写入执行相同验证及当前配额检查。来源相同且内容相同的题目映射已有题，内容不同则保留现有题并标记冲突，相关草稿、历史、进度与计划跳过，以免错绑。恢复绝不覆盖现有草稿、历史、进度、计划、设置。若原题目 ID 对应题目已删除，悬空历史等从属项明确跳过。保留现有来源 URL 唯一索引；冲突副本另存需独立设计，不在第一批中弱化并发去重。
